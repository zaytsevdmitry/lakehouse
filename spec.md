1. Архитектурный стек и инфраструктура
   Модуль предназначен для визуального проектирования, редактирования и версионирования декларативных конфигураций (метаданных) платформы Lakehouse. Приложение проектируется как универсальное корпоративное решение (White-label/On-Premise), адаптируемое под инфраструктурные контуры заказчика через конфигурационный файл application.yaml.
   Компоненты стека:
   • Бэкенд: Приложение на Spring Boot. Служит API-шлюзом, проксирует запросы фронтенда к микросервисам lakehouse, управляет жизненным циклом изолированных воркспейсов и раздает статический фронтенд.
   • Фронтенд: Одностраничное приложение (SPA) на базе React (сборщик Vite). Сборка осуществляется в директорию src/main/resources/static бэкенда. Для визуализации и изменения вычислительных графов (DAG) используется библиотека React Flow.

2. Архитектура рабочих пространств (Multi-User Workspaces)
   Для обеспечения одновременной бесконфликтной работы нескольких пользователей на сервере реализуется паттерн Server-Side Workspaces с абстракцией над типом файловой системы.
   2.1. Изоляция рабочих пространств
   При выборе пользователем ветки в интерфейсе, система выделяет ему изолированное рабочее пространство (Workspace). Идентификатором пространства на сервере выступает хэш-строка: md5(user_id + branch_name).
   2.2. Абстракция подсистемы хранения (Storage Layer)
   Конфигуратор должен поддерживать два взаимозаменяемых режима хранения файлов воркспейсов на сервере, переключаемых декларативно через application.yaml:
   1. Локальная файловая система (POSIX FS): Файлы воркспейсов раскладываются в физические директории на диске сервера или контейнера.
   2. Объектное хранилище (S3 / MinIO): Файлы хранятся в бакете в виде отдельных независимых YAML-файлов (plain text) по путям-префиксам воркспейсов. Работа с объектами происходит в потоковом режиме (Streaming) без долгосрочного удержания тяжелых Git-архивов в RAM.
      2.3. Автоматическая очистка воркспейсов
      Для предотвращения переполнения диска или S3-бакета бэкенд реализует фоновый процесс очистки (Scheduled Task). Жизненный цикл неактивных воркспейсов настраивается глобальным параметром времени жизни (параметр cleanup-ttl-hours). По истечении этого времени папка или префикс с файлами удаляются.

3. Подсистема авторизации на базе RBAC
   Вся модель разграничения прав доступа строится на ролях, настраиваемых в Keycloak (в рамках конкретного Realm или Client) и проверяемых на бэкенде через Spring Security. Центральный Git-сервер взаимодействует с Конфигуратором через системный технический аккаунт, а права реальных пользователей валидируются кодом приложения.
   3.1. Матрица ролей и прав доступа (RBAC Matrix)
   Каждому запросу от фронтенда должен соответствовать JWT-токен Keycloak, содержащий одну или несколько из следующих ролей:
   Роль в Keycloak	Доступ к API / Интерфейсу	Разрешенные операции с файлами и Git
   LAKEHOUSE_MODELLER_VIEWER	Только чтение (Read-Only)	Просмотр дерева файлов, открытие форм, визуализация графов React Flow. Кнопки «Сохранить», «Создать файл» и «На ревью» заблокированы.
   LAKEHOUSE_MODELLER_EDITOR	Чтение и запись в Workspace	Все права Viewer, плюс: создание веток, добавление/модификация файлов (сохранение на диск/в S3 воркспейса), отправка ветки на ревью в центральный Git.
   LAKEHOUSE_MODELLER_ADMIN	Полный доступ (Admin)	Все права Editor, плюс: принудительное удаление чужих неактивных воркспейсов, изменение параметров очистки, просмотр логов синхронизации.
   3.2. Механизм сквозного аудита и подмены автора в Git
   Так как пуш в центральный Git (GitLab, GitHub, Gerrit или локальный git-server) выполняется под единой системной учетной записью Конфигуратора, система гарантирует 100% отслеживаемость авторов изменений:
   1. При нажатии кнопки «Отправить на ревью» Spring Security извлекает из контекста безопасности текущий JWT-токен Keycloak пользователя.
   2. Из токена вычитываются атрибуты (claims): name (Имя и Фамилия) и email (Корпоративная почта).
   3. При формировании коммита через библиотеку JGit эти данные принудительно подставляются в метаданные коммита:
      ◦ Author ──► Заполняется данными пользователя из JWT-токена (name, email). Он фиксируется как реальный автор изменений.
      ◦ Committer ──► Заполняется техническими данными сервиса (lakehouse-modeller-svc).

4. Структура конфигурации (application.yaml)
   Пример настройки приложения для инфраструктуры с использованием S3-хранилища воркспейсов, ролевой модели авторизации через Keycloak и системного SSH-доступа к центральному Git:
```yaml
lakehouse:
  configurator:
    # 1. Настройка хранилища воркспейсов сервера
    storage:
      type: "s3" # Варианты: [local, s3]
      root-directory: "/tmp/lakehouse-workspaces" # Для local: корневой путь на диске
      s3: # Настройки для типа s3 (MinIO / AWS)
        endpoint: "http://172.20.193.200:9000"
        bucket: "lakehouse-metadata-workspaces"
        access-key: "minio-root-user"
        secret-key: "minio-root-password"
      cleanup-ttl-hours: 4 # Время жизни неактивного воркспейса до автоматического удаления

    # 2. Настройка интеграции с Центральным Git репозиторием
    vcs-provider: "local-git" # Варианты: [local-git, gitlab-api, github-app, gerrit-ssh]
    git:
      remote-url: "git://172.20.193.200/srv/git/metadata.git"
      branch-main: "main"

    # 3. Настройка режима авторизации и системного аккаунта для Git
    auth-strategy: "jwt-rbac" 
    security:
      oauth2:
        resourceserver:
          jwt:
            issuer-uri: "https://corp.internal"
            jwk-set-uri: "https://corp.internal/protocol/openid-connect/certs"
    vcs-system-account:
      auth-type: "ssh" # Варианты: [ssh, token, basic]
      ssh-private-key-path: "/secrets/git_system_ssh_key"

```
5. Модель данных и маппинг файлов (YAML to DTO)
   Все файлы метаданных хранятся в репозитории в формате YAML. Каждый файл содержит обязательное корневое поле kind, определяющее тип Java DTO класса для автоматической десериализации и генерации форм:
   • kind: NameSpace ──► org.lakehouse.client.api.dto.configs.NameSpaceDTO
   • kind: Driver ──► org.lakehouse.client.api.dto.configs.schedule.DriverDTO
   • kind: DataSet ──► org.lakehouse.client.api.dto.configs.dataset.DataSetDTO
   • kind: Schedule ──► org.lakehouse.client.api.dto.configs.schedule.ScheduleDTO (управляет графом scenarioActEdges)
   • kind: MetricDQ ──► org.lakehouse.client.api.dto.dq.MetricDQStatusDTO

6. Требования к интерфейсу пользователя (UI/UX)
   Интерфейс разделен на три зоны: Панель инструментов (Top), Дерево файлов (Left), Рабочая область/Форма (Right).
   6.1. Левая панель: Дерево файлов проекта
   • Отображает структуру каталогов текущего воркспейса пользователя (Namespaces, Drivers, Schedules и т.д.).
   • Кнопка + (Создать файл): Размещается над деревом. При нажатии открывает модальное окно:
   1. Dropdown выбора типа конфигурации (kind).
   2. Поле ввода для Имени файла (например, sales_report_dag.yaml).
   • Бизнес-логика создания: Значение, введенное пользователем в поле «Имя файла», должно автоматически дублироваться на лету в поле конфигурации keyName внутри создаваемого YAML-документа.
   6.2. Правая панель: Интерактивная форма и вкладки
   • Принцип декомпозиции полей: Простые примитивные поля базового DTO выводятся на первой (основной) вкладке формы. Все сложные вложенные структуры, списки и коллекции (например, задачи внутри актов сценариев) выносятся на отдельные вложенные вкладки.
   • Компонент Графа (React Flow): Для сущностей, содержащих направленные ациклические графы (например, ScheduleDTO с коллекцией scenarioActEdges), на отдельной вкладке визуализируется интерактивный граф. Связывание узлов стрелками автоматически наполняет коллекцию объектов DagEdgeDTO (поля from и to).
   • Кнопка «Сохранить»: При нажатии отправляет измененный JSON на бэкенд, который сериализует его в YAML и физически перезаписывает файл в текущем воркспейсе (на диске сервера или в S3 в виде текста). Если у пользователя роль LAKEHOUSE_CONFIG_VIEWER, кнопка заблокирована.

7. Жизненный цикл сценария «Отправить на ревью»
   Когда пользователь с ролью LAKEHOUSE_MODELLER_EDITOR завершает работу и нажимает кнопку «Отправить на ревью»:
   1. Бэкенд временно блокирует воркспейс пользователя на чтение/запись через UI.
   2. Бэкенд считывает финальный набор YAML-файлов из папки воркспейса (POSIX FS или S3 по префиксу).
   3. Инициализируется JGit-сессия, сервис подключается к Центральному Git под своими системными правами (vcs-system-account).
   4. Формируется итоговый коммит, куда в поле Author прописываются name и email текущего пользователя из Keycloak.
   5. Выполняется git push коммита в центральный репозиторий.
   6. В зависимости от настройки vcs-provider Конфигуратор инициирует создание ревью (создает Merge Request в GitLab/GitHub API или пушит коммит в виртуальную ветку refs/for/* для Gerrit).
   7. Временное рабочее пространство воркспейса (папка на диске или префикс в S3) удаляется.
